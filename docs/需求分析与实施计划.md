# 大肥鱼小组工作台 · 需求分析与实施计划

> 版本：v0.1（初稿，待团队确认）
> 日期：2026-10-19

## 1. 产品定位

**一句话**：面向高校学生小组的"AI 协作写作台"——把多人分头写的作业/论文，合成一篇风格统一、格式规范、引用可靠的成品。

**目标用户**
- 主要：本科生/研究生的课程小组作业、竞赛论文、毕业论文写作团队（3–6 人）
- 次要：单人写作者（用它的排版与文献功能）

**核心痛点**
1. 各写各的，合起来像四个人写的四篇文章（风格割裂、术语不一）
2. 拼接处生硬，没有过渡
3. 分工靠微信群喊，谁写了什么、进度如何无据可查
4. 数据/文献现找现编，来源不可靠
5. 排版（字体、标题层级、页码、参考文献格式）反复返工

**差异化**：市面上"AI 写作工具"多是单人生成；本产品是**多源汇聚 + 一致性治理 + 可溯源**，且输出符合国内学术规范（GB/T 7714-2015）。

## 2. 功能拆解与验收标准

| # | 功能 | 输入 | 输出 | 验收标准 |
|---|---|---|---|---|
| F1 | 多部分整合 | 多名成员的 docx/md/纯文本 | 结构完整的单一文稿 + 冲突报告 | 标题层级自动归一；重复段落被标记；不丢内容 |
| F2 | 分工记录 | 成员名单、任务 | 看板 + 贡献度统计 | 每人任务/状态/截止日可见；提交量可统计 |
| F3 | 过渡内容撰写 | 相邻两节内容 | 1–2 段衔接文字 | 承接上文、引出下文；可一键接受/重生成 |
| F4 | 用语风格统一 | 全文 + 风格基准 | 改写稿 + 逐句 diff | 术语表统一；句式风格收敛；语义不变（diff 可回退） |
| F5 | AI 辅助排版 | 文稿 + 模板 | 规范 docx/pdf | 标题/字体/行距/页码/目录正确；参考文献自动编号 |
| F6 | 数据助手 | 含缺口数据的段落 | 带来源的数据建议 | 每条数据必附 URL/来源；可插入并自动标注 |
| F7 | 参考文献助手 | 概要/大纲/段落 | 候选文献列表 + 引用条目 | 真实可访问；去重；一键生成 GB/T 7714 或 APA 条目 |

## 3. 技术选型（建议）

### 前端
- **Next.js 15 + TypeScript + Tailwind + shadcn/ui**：开发快、演示好看
- 编辑器：**TipTap (ProseMirror)**，天然支持"分块 + 批注 + diff 高亮"
- 状态：TanStack Query + Zustand

### 后端
- **FastAPI (Python)**：文档处理与 LLM 编排生态最好
  - `python-docx` / `docxtpl`：模板化生成 Word
  - `mammoth`：docx → HTML/结构化
  - **pandoc + citeproc + CSL**：参考文献格式化（GB/T 7714-2015 有现成 CSL）
  - `LibreOffice` 无头模式：docx → pdf
- 长任务：**Redis + RQ/Celery**（排版、批量检索是慢操作，必须异步）

### 数据
- **PostgreSQL + pgvector**：业务数据 + 项目内文档向量检索（保证全文术语/结论一致）
- 对象存储：MinIO 或本地磁盘（存上传件与导出件）

### AI 能力
- **LLM 网关**：走 OpenAI 兼容协议，抽象 provider 层，可切 DeepSeek / Qwen / GLM / OpenAI，支持降级与成本统计
- **结构化输出**：风格画像、任务拆解、引用条目一律用 JSON Schema 约束，避免解析失败
- **网页搜索**：Tavily / Serper / Brave / SearXNG（自建兜底）
- **学术检索**：**OpenAlex、Crossref、Semantic Scholar**（免费、有元数据、直接出 BibTeX）——这是文献功能的基石，比纯网页搜索可靠得多
- 中文库（知网等）无公开 API → 用网页搜索 + DOI 回填兜底

## 4. 系统架构

```
[Next.js 前端]
   │  REST / SSE 流式
   ▼
[FastAPI 后端]──┬── LLM 网关 ──► DeepSeek/Qwen/GLM
   │            ├── 检索层 ──► OpenAlex / Crossref / Tavily
   │            └── 文档层 ──► pandoc / docxtpl / LibreOffice
   ▼
[PostgreSQL+pgvector]  [Redis 队列]  [对象存储]
```

**关键设计：文档中间表示（IR）**
所有导入的文稿先解析成统一 IR（AST：标题层级、段落、图表题注、公式、引用标记），
后续的整合/改写/排版/导出全部基于 IR，而不是直接操作 docx 二进制。
这是"排版保真"和"风格统一"能同时做好的前提。

## 5. 数据模型（核心表）

- `users` / `projects`（项目=一门课的作业或一篇论文）
- `members`（角色：组长/成员；权限）
- `sections`（章节树：层级、负责人、状态、当前内容、IR）
- `assignments`（分工：谁、做什么、截止日、状态、完成度）
- `versions`（每次 AI 改写/合并的快照，可回滚、可 diff）
- `style_profiles`（从样章提取的风格基准：术语表、句长、人称、语气）
- `references`（文献元数据 + DOI + BibTeX）
- `citations`（正文引用点 ↔ 文献的映射）
- `evidence_logs`（数据助手的每条数据来源，用于溯源与审计）

## 6. 关键难点与风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **幻觉（最致命）** | 数据助手/文献助手编造数字和文献，学术上等于作弊 | 强制"无来源不出结论"；数据必须给可点开的 URL；文献必须来自 OpenAlex/Crossref 真实记录；界面明确标注"AI 建议，请核实" |
| **排版保真** | 直接改用户 docx 极易破坏格式 | 走"模板 + IR 渲染"路线，不反向修改原件；提供预览再导出 |
| **长文上下文** | 几万字论文超上下文窗口 | 分节处理 + 向量检索召回相关上下文 + 缓存风格画像 |
| **中文文献检索** | 知网无 API | OpenAlex/Crossref 覆盖英文；中文走网页搜索 + DOI 回填，并如实告知覆盖范围 |
| **成本与延迟** | 全文改写 token 量大 | 按需触发（只改被标记的段落）、结果缓存、小模型做分类/抽取 |
| **隐私** | 未发表论文上传到第三方 | 传输加密、可私有化部署、明确数据保留策略、演示时用假数据 |
| **学术诚信** | "统一风格"可能被视为代写 | 定位为"辅助"：所有 AI 输出需人工确认，保留 diff 与修改记录，可导出"AI 参与说明" |

## 8. MVP 建议与演示脚本

**MVP（优先做）**：F1 整合 + F2 分工 + F3 过渡 + F4 风格统一 + F5 排版导出
→ 这条链已能完整讲出"四人分头写 → 合成一篇规范论文"的故事。

**F6/F7** 放在第二批，因为检索质量直接决定演示成败，需要更多调优时间。

**演示脚本（3 分钟）**
1. 建项目，拉 3 个成员，分配章节 → 看板显示进度
2. 三人各自上传自己那段（风格故意写得不一样）
3. 一键整合 → 冲突报告指出 2 处术语不一致
4. 生成过渡段 → 两节之间补上衔接
5. 统一风格 → 展示逐句 diff，术语"神经网络/类神经网络"被统一
6. 数据助手补上缺失的统计数字 → 点击来源链接可见原文
7. 一键排版导出 → 打开 docx，标题层级、目录、参考文献（GB/T 7714）全部规范

## 9. 待确认决策

1. **交付形态**：只做本地演示，还是要部署到公网（评委能直接访问）？
2. **AI 提供方**：有无可用的 API Key / 预算？倾向国内（DeepSeek、通义、智谱）还是 OpenAI？
3. **团队技术栈**：成员更熟 Python 还是 JS？是否接受"Next.js + FastAPI"双端结构？
4. **论文语言**：以中文论文为主，还是中英都要？
5. **参考文献范围**：能否接受以 OpenAlex/Crossref（英文文献为主）为核心，中文文献用网页搜索兜底？
6. **参赛时间线**：距离提交/答辩还有多久？这决定 MVP 砍到什么程度。
