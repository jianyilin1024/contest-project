## 第一章　项目概述

### 1.1 项目背景

高校课程中的"小组作业"几乎都以一种固定形态结束：每位成员各写一部分，最后由一个人在截止日前夜把它们拼在一起。拼接的瞬间会集中暴露四类问题：

1. **章节拼接生硬**——上一位同学写"综上所述，本章分析了……"，下一位同学直接从"数据集采用 ImageNet"开始，中间没有任何承接；
2. **行文风格割裂**——有人习惯"我们认为"，有人通篇被动语态，术语也各写各的（"神经网络"与"类神经网络"混用）；
3. **排版格式不统一**——字号、行距、编号层级、参考文献格式五花八门；
4. **参考文献缺失或不可靠**——要么忘了写，要么凭印象编造一条"看起来像"的引用。

现有工具解决的是**单点问题**：Word 能排版但不理解语义，语法检查工具能改错但不统一风格，文献管理软件需要人工录入。**没有一个工具面向"把多人分段写的内容合成一篇可交的稿子"这个完整流程。**

### 1.2 项目定位

本项目的定位不是"万能写作助手"，而是**面向小组协作场景的成稿工作台**：把一个学期里分散在多人手里、风格各异的章节，加工成一篇结构统一、行文连贯、引用可靠的文稿。

一句话概括：**"把七个脑袋写的东西，变成一支笔写出来的样子。"**

### 1.3 主要成果

| 指标 | 数值 |
|---|---|
| 功能模块 | 7 个（F1–F7）+ 1 条一键成稿主链路 |
| 代码规模 | Python 7,793 行（72 文件）+ TypeScript 5,331 行（25 文件） |
| 后端接口 | 27 个 |
| 自动化测试 | 117 个用例 |
| 数据库表 | 3 张（项目 / 成员 / 任务） |
| 外部数据源 | 4 个（OpenAlex / Crossref / Open Library / DeepSeek 搜索） |
| 一键成稿耗时 | 线上实测 8–16 秒 |
| 部署形态 | 5 容器（nginx / web / api / db / redis） |

## 第二章　需求分析

### 2.1 用户与场景

**核心用户**：高校本科生与研究生，3–6 人小组，需要交付课程论文、课程设计报告、竞赛文档。

**典型流程**：

```
分工 → 各自写作（1–3 周）→ 汇总（1 晚）→ 排版（1 晚）→ 提交
             ↑ 问题集中爆发在这里
```

**痛点频次调研**（对身边 20 名同学的访谈，非严格统计，仅作需求参考）：

| 痛点 | 提及率 |
|---|---|
| 章节之间衔接生硬 | 18/20 |
| 风格与人称不统一 | 15/20 |
| 排版格式混乱 | 14/20 |
| 参考文献不会写 / 格式错 | 13/20 |
| 不知道谁该写哪一章 | 9/20 |
| 段落里缺数据支撑 | 8/20 |

这份访谈直接决定了功能优先级：**合并与衔接最痛，文献与排版其次，分工管理属于"锦上添花但确实需要"。**

### 2.2 功能需求

| 编号 | 功能 | 需求描述 | 对应痛点 |
|---|---|---|---|
| F1 | 多部分整合 | 解析 docx/md/txt，抽取章节层级，归一标题，检测重复段落与重复术语，合并导出 | 拼接生硬、结构混乱 |
| F2 | 分工记录 | 建项目、拉成员、派任务、看板跟踪进度与截止日期 | 不知道谁写哪章 |
| F3 | 过渡段落生成 | 定位章节断点，按多种语气给备选，勾选后插入 | 章节衔接生硬 |
| F4 | 用语风格统一 | 逐段改写为统一学术书面语，**逐句可接受/回退** | 风格割裂 |
| F5 | AI 辅助排版 | 模板化 docx 生成，自动编号、目录、页码，参考文献规范化 | 格式混乱 |
| F6 | 数据助手 | 找出"该有数据却没数据"的地方，联网检索并给出带来源的建议 | 段落缺乏支撑 |
| F7 | 参考文献 | 检索真实文献，按 GB/T 7714-2015 格式化，可逐条编辑 | 引用缺失、格式错 |
| 主链路 | 一键成稿 | 合并 → 过渡 → 文献 → 排版，一次完成 | 全流程 |

### 2.3 非功能需求

| 类别 | 要求 | 设计应对 |
|---|---|---|
| 可信性 | **绝不能编造文献与数据** | 所有外部事实必须溯源；来源不在本轮检索结果中一律丢弃 |
| 可控性 | 用户对 AI 输出有最终决定权 | 过渡段勾选、风格逐句接受、文献逐条可编辑 |
| 响应时间 | 单功能 ≤ 20 秒，一键成稿 ≤ 30 秒 | 并发检索、批处理、超时降级 |
| 鲁棒性 | 任一 AI 环节失败不得导致整体失败 | 分步降级，失败原因写入步骤日志 |
| 部署成本 | 2 核 2G 服务器可运行 | 多阶段镜像、依赖极简化、内存上限约束 |

### 3.2 技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | Next.js 16（App Router） | 服务端渲染 + 静态预渲染兼顾；standalone 输出便于容器化；文件路由与功能分区天然对应 |
| 前端语言 | TypeScript 6（strict） | 接口契约多（27 个），类型是最好的一致性检查 |
| 样式 | Tailwind CSS 4 | 设计系统通过 token 统一，避免散落的样式文件 |
| 后端框架 | FastAPI | 异步原生支持（AI 调用密集）；Pydantic 自动校验；OpenAPI 自动生成，便于自查接口 |
| 后端语言 | Python 3.11 | 文档处理生态成熟（python-docx、lxml）；AI 生态首选 |
| 数据库 | PostgreSQL 16 + SQLAlchemy 2（async） | 关系型足够；异步驱动与 FastAPI 一致；预留 pgvector 供后续语义检索 |
| 缓存 | Redis 7 | 限流与短期缓存，内存占用限制在 64MB |
| 部署 | Docker Compose + nginx | 单机 5 容器，成本最低；CI 构建镜像，服务器只拉取 |

**为什么不用微服务**：本项目单机部署、用户量小，拆服务只会增加运维复杂度而不带来收益。**分层单体 + 清晰的模块边界**是更合适的选择。

### 3.3 关键数据结构：文档中间表示（IR）

所有格式先转换为统一 IR，后续所有功能都基于 IR 工作——这是"一次解析、多处复用"的关键设计。

```python
@dataclass
class Block:
    kind: str          # paragraph | list_item | table | image | code
    text: str
    level: int = 0

@dataclass
class Node:
    level: int              # 标题层级 1..6
    title: str              # 归一化后的标题
    raw_title: str          # 原始标题
    blocks: list[Block]
    document: str           # 来源文档名
```

**为什么用扁平列表而不是树**：合并、重排、插入过渡段都是"在序列上操作"，扁平结构让这些操作变成简单的索引计算；需要层级时再按 level 现算，比维护树更不容易出错。

| llm | `/llm/health` | 模型连通性自检 |
| merge | `/merge/upload` 等 | F1 合并 |
| analysis | `/analysis/single`、`/unify`、`/rewrite` | 单文档分析 / 归并稿 / F4 逐段改写 |

| pipeline | `/pipeline/oneclick` | 一键成稿 |

## 第四章　AI 技术方案

> 本章是文档的重点，按"选型—集成—优化—安全"四条线展开。

### 4.1 模型选型理由

**选择 DeepSeek 系列（deepseek-flash / deepseek-v4-pro）而非 GPT 或开源本地模型**，理由有四：

1. **成本**：本项目单篇文档要调用 5–15 次模型，按量计费的成本差异会被放大。DeepSeek 的单价约为同级模型的十分之一。
2. **中文能力**：目标用户写的是中文学术文本，中文语感与学术表达的把控比英文基准更重要。
3. **推理模型特性**：本项目多处需要"先想清楚再输出"（如判断章节间是否缺过渡、判断段落缺什么数据），推理模型先产生 `reasoning_content` 再给结论，对这类判断任务的准确率明显更好。
4. **协议兼容**：OpenAI 兼容协议意味着可以随时换模型，不被厂商锁定。

**代价与应对**：推理模型输出慢、token 消耗高，因此必须做"给足 max_tokens + 并发 + 超时降级"（见 4.6）。

### 4.2 集成方式：统一 LLM 网关

后端不直接在业务代码里调 API，而是统一经过 `services/llm/` 网关。网关解决四件事：

**（1）协议适配与模型切换**

```python
class LLMProvider(Protocol):
    async def structured(self, messages, schema, *, max_tokens=4096) -> dict: ...
    async def stream(self, messages) -> AsyncIterator[str]: ...
```

业务层只依赖这个协议，换模型只改配置。

**（2）结构化输出与"截断重试"**

要求模型返回 JSON 时，最大的坑是**JSON 被截断**。网关做了三层处理：

1. 解析失败时，用正则从文本中提取第一个完整 JSON 对象（应对模型在 JSON 前后加解释）；
2. 仍然失败，则**把 max_tokens 翻倍重试一次**；
3. 二次失败才抛错，由业务层降级。

这一层把"结构化输出失败率"从偶发的 5%–10% 压到了几乎为零。

**（3）推理模型的 `reasoning_content` 处理**

推理模型会先输出思维链再输出答案，二者在不同字段。网关在流式与非流式两条路径上都做了字段合并与剥离，保证业务层只看到干净的 `content`。

**（4）分层降级**

```
业务调用 → 网关（重试/修复）
          ↓ 仍失败
        记录失败原因 → 返回可用的部分结果
          ↓
        整体流程不中断
```

### 4.3 Prompt 工程：把"不编造"写进约束

本项目所有 Prompt 共享三条原则：

**原则一：给出可判定的标准，而不是形容词。**

反例："请找出缺少数据的地方。"
实际用法："例如『该方法效果显著』缺具体准确率；『用户增长迅速』缺增长率与统计口径。纯观点、纯方法描述不算缺口。"

**原则二：明确"没有就说没有"。**

文献抽取的 Prompt 里写的是：

> 铁律：摘要里没有可复用的数字，就返回空数组。不要推断、不要换算、不要合并多个来源的数字。

**原则三：要求模型自证来源。**

```json
{"value": "准确率 87.58%", "source_title": "…", "source_url": "…",
 "quote": "原文中包含该数据的句子", "confidence": 0.85}
```

模型必须填写 `quote`（原文引用），这比只填 URL 更能抑制幻觉——因为"编一句话"比"编一个链接"更容易被察觉。

### 4.4 检索增强：四个真实数据源的编排

本项目没有用向量数据库，而是采用**"多源实时检索 + 严格溯源"**的增强方式。原因：学术文献的数据源本身就有高质量的结构化检索（OpenAlex 的相关度排序优于自建向量索引），且文献具有强时效性，实时检索比离线索引更可靠。

**四个数据源的分工**：

| 数据源 | 覆盖 | 用途 | 协议 |
|---|---|---|---|
| OpenAlex | 2.5 亿学术作品 | 论文检索主通道（免费、无需 Key） | REST |
| Crossref | DOI 元数据 | 按 DOI 补全卷、期、页码 | REST |
| Open Library | 图书 | 科普读物、教材、文学作品 | REST |
| DeepSeek 搜索 | 全网 | 科普文章、政策文件、中文资料 | REST |

**关键设计：关键词生成先于检索。**

最初直接用文档标题检索，实测效果很差——用"小组作业合并稿"这种泛标题去查，返回的全是"英语学习""小组合作"之类的无关文献。

改进方案是**先让模型把标题 + 章节 + 正文摘录转换成 3–5 组中英文关键词**，再分别检索、合并、按相关度重排：

```
「小组作业合并稿」+ 正文（讲小样本学习）
        ↓ 关键词抽取
few-shot image classification meta-learning
MAML episodic training task sampling
few-shot medical image classification limited annotations
ResNet-18 meta-learning image classification
        ↓ 分别检索 → 合并去重 → 按相关度排序
Prototypical Networks / MetaMed / Baseline for Few-Shot …
```

这一步是**整个文献功能的效果分水岭**：同一个文档，检索结果从"完全跑偏"变成"全部对题"。

**为什么必须给英文关键词**：OpenAlex 的中文文献覆盖与排序质量远弱于英文。让模型顺带生成英文对应词，等于用中文文档撬动了英文文献库。

**检索结果的二次过滤**：网页结果里混有大量噪声（PDF 片段 `[0043]…#`、导航文字"跳到主要内容"、无站点名的转载页）。系统按标题长度、噪声模式、站点名、权威度四个维度过滤后才送入模型。

### 4.5 工作流编排：一键成稿

一键成稿是四步串行工作流，但不是简单的函数调用链——**每一步都有独立的降级与观测**：

```
① 合并        解析 → 归一 → 去重 → 检测术语    （纯计算，< 100ms）
② 补过渡      IR 分块 → 定位断点 → 生成备选 → 去 AI 味   （1 次模型 + 1 次去味）
③ 检索文献    抽关键词 → 四源并发检索 → GB/T 7714 格式化   （1 次模型 + 并发 HTTP）
④ 返回成稿    拼接最终 Markdown，前端再调排版接口导出 docx
```

**每一步都返回"状态 + 耗时 + 说明"**，前端渲染成流水线，用户能看到卡在哪一步、为什么跳过。这不是装饰——当 AI 环节失败时，用户需要知道"是没找到文献，还是检索超时了"。

**并行化**：第 ③ 步的四个数据源并发请求。原先串行时聚合耗时 21 秒，并发 + 把最慢的 Open Library 超时压到 6 秒后降到 7 秒。

### 4.6 优化策略

| 优化项 | 问题 | 做法 | 效果 |
|---|---|---|---|
| **max_tokens 策略** | 推理模型思维链占 token，常导致 JSON 截断 | 一律给到需求量的 2–3 倍；截断则翻倍重试 | 结构化输出失败率趋近 0 |
| **并发检索** | 串行查询慢 | 四源 `asyncio.gather` 并发 | 21s → 7s |
| **超时分级** | 单一慢源拖垮整体 | 学术 20s / 图书 6s / 网页 40s，各自独立 | 最慢源不再决定整体 |
| **批处理 + 信号量** | 逐段改写触发大量请求 | 每批 6 段、并发 4 | 段落数线性增长但耗时不爆炸 |
| **Prompt 瘦身** | 送入模型的来源越多越慢 | 每缺口最多 5 条来源、摘要截断 500 字 | 实测 3 条时模型反而抽取不出数据，5 条是质量与耗时的平衡点 |
| **降级不阻断** | 任一环节失败导致整单失败 | 每步 try/except，失败记入步骤 | 可用性显著提升 |

> **一个反直觉的实测结论**：曾尝试"把所有缺口合并成一次模型调用"以减少请求数，结果耗时反而从 43 秒涨到 61 秒且抽取结果为空——提示词变长后模型的有效注意力被稀释。**"少调用"不等于"快"，提示词长度才是推理耗时的主导因素。**

### 4.7 AI 安全与可控性

| 机制 | 实现 | 防的是什么 |
|---|---|---|
| 来源白名单 | 建议的 `source_url` 必须命中本轮检索结果（同域或全等） | 模型编造链接 |
| 原文引用必填 | 每条建议必须附 `quote` | 模型编造数据 |
| 空结果合法 | 检索不到时明确返回空 + 提示语 | 模型为"凑数"而幻觉 |
| 信息守恒校验 | 去 AI 味改写后，检查数字、专名、引用是否被删改 | 改写时丢信息 |
| 逐句人工确认 | 风格统一返回 diff，默认只勾选真正改动的段 | 全篇不可逆改写 |
| 失败可见 | 每步状态与失败原因回传前端 | 静默失败误导用户 |

## 第五章　核心功能实现

### 5.1 F1 多部分整合

**解析层**：`parsers.py` 按扩展名分派——docx 用 python-docx 读段落与样式，md 按标题正则切分，txt 按首行推断。三者统一产出 `ParsedDocument`。

**合并层**：`merge.py` 做四件事——标题层级归一（把"1.1"“一、"“（一）"统一成 level 1/2/3）、重复段落检测（相似度超过阈值）、重复术语检测（同一概念多种写法）、章节顺序编排。

**输出**：合并后的 Markdown，可直接交给 F5 排版导出 docx。

### 5.2 F2 分工记录

三张表：`projects` / `members` / `tasks`，SQLAlchemy 2 异步 ORM。表结构在应用启动时自动创建（`init_models()`），数据库不可用时只记警告不阻断启动——这是为"比赛演示环境可能没有数据库"做的降级。

前端是三列看板：待办 / 进行中 / 已完成，任务卡上直接显示负责人与截止日期，点按钮流转状态。

### 5.3 F3 过渡段落

**断点定位**：把文档切成块，相邻两块的"话题相似度"低于阈值即判定为断点。相似度用词频重叠 + 标题关键词计算，不消耗模型。

**备选生成**：对每个断点，一次调用生成 2–3 个不同语气（简洁承接 / 展开说明 / 设问过渡）的备选。

**去 AI 味**：生成的过渡段先过一遍去味检测，再展示给用户。这一步很关键——AI 生成的过渡句最容易出现"综上所述""值得注意的是"这类模板话。

**勾选插入**：用户勾选后调用 `/transition/apply`，把段落插入 IR 对应位置并重新拼接 Markdown。

### 5.4 F4 用语风格统一

**逐段而非整篇**：整篇重写有两个致命问题——用户无法判断哪里被改了；一旦不满意只能重来。

**实现**：按行切段（跳过标题、代码块、列表、表格），每 6 段一批交给模型，返回"原文 / 改后 / 是否改动 / 改动理由"。

**一个细节**：模型有时会声称 `changed: true` 但返回的文本与原文一致。系统做二次比对——文本相同就强制置为 `changed: false`，避免让用户面对"没变却标红"的困惑。

**应用阶段**：用户勾选的段按原文文本匹配替换回去，未勾选的保持原样。

### 5.5 F5 AI 排版

模板化 docx 生成：封面、目录域、标题样式、正文样式、页码、参考文献段。

**两个工程细节**：
- 目录使用 Word 域（`TOC`），并设置 `updateFields`，打开时提示更新——纯文本目录在页码变化后会失效；
- 中文字体必须显式设置 `w:eastAsia`，否则 Word 里中文会回退到默认字体。

### 5.6 F6 数据助手

三段式：**识别缺口 → 联网检索 → 抽取数据**。

识别缺口时，模型要为每个缺口生成检索词；检索并发执行；抽取时把原文与检索结果一起送入，要求模型只从结果中抽取。

**最难的部分不是生成，而是"忍住不生成"**：实测中有一轮检索到的全是专利页和表格页，摘要里没有可用数字，模型返回空数组——这是**正确行为**。因此前端专门设计了空结果提示："这次没有找到可靠的数据来源，这是预期行为。"

### 5.7 F7 参考文献

**格式化在本地做，不交给模型。** GB/T 7714-2015 的格式是确定性的，模型反而会改错，而且没必要消耗 token。

**作者处理**是中文场景的难点：
- 西文：`Jane Smith` → `Smith J`（姓在前 + 名首字母）
- 中文：OpenAlex 有时给"孟月 宋"（名在前），需还原为"宋孟月"

**类型标记**：期刊 `[J]`、专著 `[M]`、会议 `[C]`、学位论文 `[D]`、电子资源 `[EB/OL]`。

### 5.8 一键成稿

见 4.5。核心价值不在"自动化"，而在**把四个原本需要来回切换的功能串成一条可观测的流水线**。

## 第六章　创新点

### 6.1 技术创新

**（1）基于语料统计的"去 AI 味"特征集**

不是凭感觉定义"AI 味"，而是从 283 万字语料中统计候选特征：

- 26 个候选特征中，**仅 11 个具有区分度**——其余 15 个（如"总字数""段落数"）在人机文本间无显著差异；
- 人类使用**比喻**的频率是 AI 的 2.4 倍，**反问句**是 17 倍；
- 最强的单一信号是**段首零回指评论**（4.4 倍）；
- DeepSeek 在**破折号**（5.16/千字）、**提示性冒号**（0.43/千字）、**过长前置定语**（0.65/千字）三项上显著高于人类基线。

这套特征集直接驱动改写策略，而不是笼统地"让文字自然一点"。

**（2）多源实时检索 + 零编造的引用链路**

不建向量库，而是编排四个真实学术数据源；不做"生成引用"，而是"检索 → 筛选 → 本地格式化"。**引用条目全部可点 DOI 核实**。

**（3）关键词生成先于检索**

用模型把中文标题/正文转换为中英文关键词组，再分别检索合并。这一步把中文文档的文献召回质量从"完全跑偏"提升到"全部对题"。

### 6.2 应用创新

**（1）面向"拼接"而非"写作"**

现有 AI 写作工具都在优化"从零生成"，而本项目的切入点是**"已经有内容，如何把它们变成一个整体"**——这是一个真实存在但被忽略的场景。

**（2）可逐句拒绝的 AI**

三个功能都遵循同一交互原则：**AI 提议，人来决定**。过渡段给多备选、风格统一给 diff、文献给可编辑条目。AI 不替代判断，只降低判断成本。

**（3）全过程可观测**

一键成稿把四个步骤的状态、耗时、跳过原因全部展示。用户不需要相信"它做完了"，而是能看到"它做了什么"。

## 第七章　测试与部署

### 7.1 测试策略

| 层次 | 手段 | 覆盖 |
|---|---|---|
| 单元测试 | pytest，117 个用例 | 解析、合并、去重、格式化、Prompt 组装、接口契约 |
| 契约测试 | FastAPI TestClient | 27 个接口的请求/响应结构 |
| 边界测试 | 空文档、超长文档、损坏 docx、无网络 | 降级路径 |
| 端到端 | Puppeteer 驱动真实浏览器 | 上传→生成→下载 docx 全链路 |
| 线上验证 | 部署后对 11 个路由与关键接口做实际调用 | 生产环境可用性 |

**测试中的一个设计原则**：AI 相关测试**全部打桩**（mock provider），保证测试不依赖网络与额度，且可断言具体行为（如"来源不在检索结果的建议必须被丢弃"）。

### 7.2 部署架构

```yaml
services:
  nginx:    # 反向代理 + 静态缓存，Docker DNS 动态解析上游
  web:      # Next.js standalone，3000
  api:      # FastAPI + uvicorn，8000
  db:       # PostgreSQL 16 + pgvector
  redis:    # 缓存/限流，maxmemory 64mb
```

**资源约束（2 核 2G）**：

| 服务 | 内存上限 | 实测占用 |
|---|---|---|
| db | 512 MB | 45 MB |
| api | 448 MB | 87 MB |
| web | 448 MB | 62 MB |
| redis | 96 MB | 11 MB |
| nginx | 48 MB | 5 MB |

**关键运维设计**：
- **健康检查**：api 用 Python `urllib` 自检（不额外装 curl，镜像更小）；
- **镜像由 CI 构建**并推送 GHCR，服务器只拉取（拉取超时则退回本地构建）；
- **每日 3:00 自动备份**数据库，保留 14 天；
- **nginx 故障修复**：改用 `resolver 127.0.0.11` + 变量 `proxy_pass`，解决"容器重建后 IP 变化导致全站 502"（这是本次部署踩过最痛的坑）。

### 7.3 部署过程中解决的典型工程问题

| 问题 | 现象 | 根因 | 解决 |
|---|---|---|---|
| 构建 OOM | 镜像构建被内核 kill | 安装 build-essential 峰值吃 1GB 内存 | 依赖全有 manylinux wheel，直接去掉编译器 |
| 国内镜像慢 | 拉取基础镜像卡住 | 官方源不可达 | Dockerfile 支持配置 apt/pip/npm 镜像源 |
| 全站 502 | 部署后所有页面 502 | nginx 启动时缓存上游 IP | Docker DNS 动态解析 |
| 表单开关失效 | 不传参数时功能被关闭 | FastAPI 对 bool 表单缺省值处理不符预期 | 改用字符串解析 |
| 服务器无法访问 GitHub | git pull 超时 | 网络限制 | 用 git bundle 传输提交，保持历史一致 |

## 第八章　总结与展望

### 8.1 已知不足

诚实列出，而非回避：

1. **无多模态能力**——纯文本处理，不支持图像、语音。本项目的问题域本身偏文本，但确实是一个能力缺口。
2. **不是自主 Agent**——一键成稿是"固定工作流"而非"自主规划"。没有规划器、没有动态工具选择、没有自我反思循环。
3. **检索未使用向量化**——依赖数据源自身的相关度排序，未做 embedding 语义检索。
4. **AI 输出未流式渲染**——网关支持 SSE，但页面仍用一次性返回，长任务时用户只能看转圈。
5. **前端性能优化有限**——未做显式懒加载与代码分割。
6. **单实例部署**——2 核 2G 单机，无水平扩展能力。
7. **无用户体系**——分工记录的数据是全局的，没有登录与权限隔离。

### 8.2 展望

**近期（可在一个迭代内完成）**

- 接入流式输出，把"等待 15 秒"变成"逐字生成"；
- 前端路由级代码分割与图片优化；
- 分工记录增加成员账号，做到数据隔离；
- 文献库支持用户在本地维护"已收藏文献"，减少重复检索。

**中期**

- 引入 pgvector，把检索到的高质量文献做成可复用的语义索引；
- 把现有工具（合并、检索、排版）封装成 **MCP Server**，让其他 AI 客户端也能调用；
- 一键成稿增加"规划—执行—自检"环路，向真正的 Agent 演进。

**长期**

- 从"成稿工具"延伸为"课程作业质量基础设施"：为教师提供风格一致性与引用规范性检查；
- 探索可解释的写作质量评分，帮助学生理解"为什么这段读起来不像一个人写的"。

### 8.3 一句话总结

**这个项目想证明的是：AI 不必替人写，它可以只做那件人最不愿意做、又最容易做砸的事——把七零八落的东西拼成一篇像样的文章。**
